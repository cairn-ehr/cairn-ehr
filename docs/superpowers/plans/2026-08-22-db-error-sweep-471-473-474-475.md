# Finishing the `db error` sweep — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended)
> or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax
> for tracking.

**Goal:** Close the four issues PR #472 raised and could not absorb — #473, #474, #475, #471 — so that
every remaining place a database failure reaches an operator in `cairn-node` and on `cairn-sync`'s two
loop paths names the migration, the SQLSTATE, the server's message and its DETAIL/HINT, and so the
`db_errors_stay_legible.rs` guard can widen from one file to three.

**Architecture:** Three moves, in order of how much they add.

1. **Rendering** — route the remaining `tokio_postgres::Error` / `postgres::Error` renderings through the
   existing `legible_db_error` on each side. Nothing new; `crates/cairn-node/src/db_diagnosis.rs` and
   `crates/cairn-sync/src/main.rs::legible_db_error` already compose the byte-identical shape.
2. **Preserving the cause while rendering it** — `anyhow!("…: {}", legible_db_error(&e))` *discards the
   source*, which is fine in `db.rs` (nothing downstream reads it) but fatal in `cairn-node`'s
   `sync.rs`, where `run`'s catch-all must tell a local database failure from a partition (#474 item 3 =
   #469 in the other crate). So this plan adds **one** small type — `db_diagnosis::LocalDbFault` — that
   renders legibly *and* keeps the `tokio_postgres::Error` reachable through `source()`. Classification
   then becomes a pure predicate over the error chain.
3. **Reporting partial work** — #471 is not a rendering bug at heart: `do_requeue` loses the whole
   report of what it achieved when a mid-loop statement fails. It gets `CursorCommitError`'s shape
   (a typed error carrying the partial metrics), which is #469's worked example in the same file.

**Tech Stack:** Rust 1.96 (pinned, `rust-toolchain.toml`), `tokio-postgres` 0.7 / `postgres` 0.19,
`anyhow`, PostgreSQL 18 + `cairn_pgx`. No new dependencies (house rule 1: none to license-check).

**Spec:** the four GitHub issues are the spec —
[#473](https://github.com/cairn-ehr/cairn-ehr/issues/473),
[#474](https://github.com/cairn-ehr/cairn-ehr/issues/474),
[#475](https://github.com/cairn-ehr/cairn-ehr/issues/475),
[#471](https://github.com/cairn-ehr/cairn-ehr/issues/471) — each of which carries its own acceptance
criterion, quoted verbatim in the task that closes it. The governing decision is
[ADR-0060](../../spec/decisions/0060-partial-validity-a-defect-on-one-line-never-invalidates-another.md)
decision 2 (partial completion must be reported, never implied) and the principle-4 rule #469 applied to
a metric: **a failed write must not report the values it meant to set.**

## Paper-parity (§1.2)

**Paper-parity: not clinical-surface — every change here is operator-facing diagnostic text on stderr and
one JSON metrics object. No clinical workflow gains, loses or reorders a human act; no clinician-visible
surface changes.** #473 is *reached from* a clinical write path (`medication/coding.rs:166`), but what it
changes is the line an operator reads when an advisory decoration fails; the write itself is untouched, and
ADR-0060's "an advisory lookup never cancels a clinical write" stays exactly as it is.

## Global Constraints

- **AGPL-3.0**, no new dependencies.
- **TDD** — failing test first, run it, watch it fail *for the stated reason*, then implement. Every new
  test must be mutation-checked: break the fix, confirm the test goes red, restore.
- **House rule 3** — every non-trivial function carries a comment saying *why* it exists for a junior
  reader, not what the next line does.
- **House rule 4** — pure functions with explicit inputs/outputs wherever the logic can be lifted out of
  I/O; the classifier, the label builder and the message composers all must be unit-testable with no
  database.
- **`SCHEMA_GENERATION` stays 50.** No `db/*.sql` file is created or edited by this plan. No new ADR:
  every decision here is an application of ADR-0060 and of #467/#469's already-taken decisions.
- **The connection string is never echoed** into any error or log line — it can carry a password. This is
  `db.rs::connect`'s existing rule (PR #472) and it binds every new site here.
- **A number is a claim.** Where a read or a write fails, report `null`, never `0`
  (`references_unlearnable`'s rule; #465/#469).
- **Test databases are shared.** To force a write failure, hold a `FOR UPDATE` row lock from a second
  connection under a short `lock_timeout`. Never install a trigger or a `REVOKE`: those persist if the
  test panics and poison every later suite (the 2026-08-22 session's reusable mechanic).
- Run cargo with a scratch target dir so a live IDE's rust-analyzer does not hold the shared lock:
  `CARGO_TARGET_DIR=/tmp/cairn-sweep`.

### Task 2: `LocalDbFault` — render legibly *and* keep the cause reachable

**Files:**
- Modify: `crates/cairn-node/src/db_diagnosis.rs` (add the type + its unit tests)

**Interfaces:**
- Consumes: `compose_db_diagnosis`, `legible_db_error` (both in this module).
- Produces:
  - `pub struct LocalDbFault` with `pub fn new(context: &str, source: tokio_postgres::Error) -> Self`;
  - `impl Display` → `"{context}: {legible}"`;
  - `impl std::error::Error` with `fn source() -> Some(&self.source)`;
  - so `anyhow::Error::from(LocalDbFault)` renders legibly at `{e}` **and**
    `err.chain().any(|c| c.is::<tokio_postgres::Error>())` is still true.

**Why this exists and why `anyhow!` will not do:** `db.rs` renders with
`anyhow!("…: {}", legible_db_error(&e))`, which is correct there because nothing downstream reads the
cause. In `sync.rs` something does: `run`'s catch-all has to tell "this node's database failed" from
"the peer did not answer" (#474 item 3), and `anyhow!` **moves the rendered string in and drops the
error**, so the chain is empty and every local fault would classify as a partition — the exact defect
#469 records, reproduced by the fix for it.

```rust
/// A database failure from **this node's own database**, rendered for a human without
/// throwing away the error underneath it.
///
/// # Why a type and not another `anyhow!`
///
/// `db.rs` renders its failures as `anyhow!("…: {}", legible_db_error(&e))`, and that is
/// right there: nothing downstream of the schema loader reads the cause, so moving the
/// rendered string in and dropping the error costs nothing.
///
/// `sync.rs` is different. Its `run` loop must tell two failures apart that look identical
/// from the outside — *this node's database failed* and *the peer did not answer* — because
/// they send an operator to two different places, and calling the first one a partition
/// charges link downtime for a local write failure (issue #474 item 3; issue #469 is the
/// same defect in `cairn-sync`, where the fix is a distinct error class). Classification
/// walks the error chain, so the chain has to still be there. `anyhow!` empties it: the
/// macro takes a formatted STRING, so the `tokio_postgres::Error` is consumed by the
/// `format!` and never becomes anyone's `source()`.
///
/// So this type does both jobs: `Display` is the legible rendering an operator reads, and
/// `source()` is the original error a classifier can find.
///
/// # Why the rendering happens at construction
///
/// `legible_db_error` is called once, in [`LocalDbFault::new`], and the result is stored.
/// A `Display` impl that rendered on every call would re-walk the source chain for every
/// log line and — worse — would make the cost of formatting depend on how deep the chain
/// is, on an error path. Rendering once, at the site that knows the context, is both
/// cheaper and easier to reason about.
#[derive(Debug)]
pub struct LocalDbFault {
    /// What this node was trying to do — the caller's own words, e.g. `"checkpointing
    /// sync cursor"`. Never the connection string: it can carry a password.
    context: String,
    /// The `legible_db_error` rendering of `source`, computed once at construction.
    rendered: String,
    /// The original error, kept so [`std::error::Error::source`] can hand it back. This is
    /// the field the whole type exists for.
    source: tokio_postgres::Error,
}

impl LocalDbFault {
    /// Wrap a failed database call with what it was doing.
    ///
    /// `context` is a short phrase in the caller's own words, and it must never contain a
    /// connection string, a password, or unbounded text from a peer — it is spliced into a
    /// one-line operator log.
    pub fn new(context: &str, source: tokio_postgres::Error) -> Self {
        let rendered = legible_db_error(&source);
        Self {
            context: context.to_string(),
            rendered,
            source,
        }
    }
}

impl std::fmt::Display for LocalDbFault {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        write!(f, "{}: {}", self.context, self.rendered)
    }
}

impl std::error::Error for LocalDbFault {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        Some(&self.source)
    }
}
```

/// A real `tokio_postgres::Error` with a live `source()`, built with no database and no
/// network — `Config`'s own parser produces one.

```rust
/// What kind of failure ended a pull cycle? (#474 item 3; #469 is the same distinction in
/// `cairn-sync`.)
///
/// The two send an operator to two entirely different places, so collapsing them is not a
/// cosmetic loss: `Partition` means *go and look at the link*, and it is what an
/// availability figure is charged against. Calling a failed local `UPDATE` a partition
/// spends an operator's attention on a healthy WAN and understates this node's own uptime.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum PullFailureClass {
    /// **This node's own database** failed. The peer and the link were never the problem —
    /// on this path they may not even have been reached.
    LocalFault,
    /// The peer did not answer. The default, by elimination.
    Partition,
}

/// Classify a failed pull. **Pure**, so the mapping is unit-testable over constructed
/// errors rather than being reachable only by breaking a live database mid-cycle.
///
/// # Why it walks the chain rather than inspecting the outermost error
///
/// Every database call on this path is wrapped — `LocalDbFault` adds the context an
/// operator needs, and callers may add a `.context()` of their own on top. A classifier
/// that looked only at the outermost type would classify all of those as `Partition`,
/// silently, which is precisely the defect this function exists to fix. `anyhow::Error`'s
/// `chain()` walks `source()` to the bottom, so a wrapper anywhere on the path is harmless.
/// (`cairn-sync`'s sibling `classify_pull_failure` carries the opposite caveat because
/// `downcast_ref` on a `dyn Error` does NOT walk the chain — the two crates reach the same
/// answer by different routes, and the difference is worth knowing before porting a change
/// from one to the other.)
///
/// # Why the default is `Partition` and why it is LAST
///
/// A failure this function does not recognise is, by elimination, one where the peer did
/// not answer. Every failure that IS local must therefore be claimed explicitly above. The
/// asymmetry is deliberate: an unclaimed local fault becomes a partition and misdirects an
/// operator, so the recognised arm is the one that must be kept complete — which is why the
/// test file pins a bare error, a wrapped one and a doubly-wrapped one.
pub fn pull_failure_class(e: &anyhow::Error) -> PullFailureClass {
    if e.chain().any(|c| c.is::<tokio_postgres::Error>()) {
        return PullFailureClass::LocalFault;
    }
    PullFailureClass::Partition
}
```

- [ ] **Step 3: Implement the error type and the message**

Beside `CursorCommitError` in `crates/cairn-sync/src/main.rs`:

```rust
/// A `requeue` that failed PART-WAY THROUGH its loop, carrying what it had achieved
/// (issue #471; ADR-0060 decision 2).
///
/// The three statements inside `do_requeue`'s loop were bare `?`, so a failure on row 5 of
/// 20 returned a raw `postgres::Error` and the whole metrics object went with it. At that
/// moment rows 1-4 HAVE been released — their events are durable in `event_log` and their
/// pen rows are gone — and rows 6-20 were never examined. Reporting nothing at all about
/// either is exactly the implied-completion ADR-0060 decision 2 forbids: an operator
/// re-runs the command (correctly — release is idempotent through the db/020 door) with no
/// way to know from the failed run what it had already done, or whether the four rows that
/// vanished from the pen were released or lost.
///
/// Modelled on [`CursorCommitError`], which is the same decision one command over, and for
/// the same reason: the metrics have to survive the `Err`, so they travel inside it.
#[derive(Debug)]
struct RequeueInterruptedError {
    message: String,
    /// The counts as they stood when the statement failed, with `references_unlearnable`
    /// held at `null` — the #465 report never ran, and `0` would be a claim that it had.
    metrics: serde_json::Value,
}

impl std::fmt::Display for RequeueInterruptedError {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.write_str(&self.message)
    }
}

impl Error for RequeueInterruptedError {}

/// Compose the sentence an operator reads when a requeue is interrupted. **Pure.**
///
/// Every clause earns its place: the counts say what is DONE and durable, the digest says
/// WHERE it stopped (so the untouched remainder is knowable), the cause says why — it was
/// `db error` before — and the remedy is stated because it is real: release runs through
/// the same in-DB door a pull does, so re-running after fixing the fault is safe and
/// re-releases nothing twice.
fn requeue_interrupted_message(
    examined: usize,
    released: usize,
    still_quarantined: usize,
    vanished: usize,
    at: &str,
    cause: &str,
) -> String {
    format!(
        "requeue: INTERRUPTED at {at} after examining {examined} pen row(s) — this node's \
         own DATABASE failed: {cause}. Work already done is NOT lost: {released} released \
         (durable in event_log, their pen rows gone), {still_quarantined} still held, \
         {vanished} vanished before release. The remaining rows were never examined. The \
         attachment-reference report did not run, so it reports null rather than zero. Fix \
         the local database fault and re-run — release goes through the same in-DB door a \
         pull does, so it is idempotent."
    )
}
```

**One risk worth flagging before execution.** Task 3 converts twelve `.context()` calls to `.map_err`.
`anyhow::Context` and `map_err` differ in one way that bites: `.context()` works on any `Result` whose
error is `Send + Sync + 'static`, while `.map_err(|e| LocalDbFault::new(…, e))` requires the error to be
exactly `tokio_postgres::Error`. If any of the twelve sites is *not* a `tokio_postgres::Error` the
compiler will say so immediately — treat a compile error there as a signal to leave that site on
`.context()`, not to force the conversion.
