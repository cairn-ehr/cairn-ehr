# Trap-clearing pass — six gates that reassure without earning it

**Goal:** close the six issues PR #448's review left behind, all of the same species that PR set out
to close: *a gate that supplies confidence without earning it.* Two are guards whose own trigger is
unverified (#449, #450), one is the same hole one language over (#451), one is a convention followed
by all-but-two of a family (#453), one is a migration that is loaded but never driven (#386), and one
is a duplication that has already caused two of three copies to miss a fix (#452).

**Architecture:** no new event type, no new migration file, no ADR. Two in-place `CREATE OR REPLACE`-
adjacent SQL edits (REVOKE/GRANT lines beside their definitions, the db/005 + db/015 idiom #443
established), one new shared test-only leaf module, one new Python guard, three edited Rust guards,
one CI workflow `env:` declaration, one CONTRIBUTING section.

**Tech Stack:** Rust (`cairn-node`, `cairn-sync`), Python (`matcher`, via uv), PostgreSQL 18 +
`cairn_pgx`, GitHub Actions. No new dependencies in any tree.

Paper-parity: not clinical-surface — every item is a test-suite or CI guard below the enforcement
floor; none adds, removes or reshapes a clinical workflow, and no clinician-visible step count moves.

## Global Constraints

- **AGPL-3.0**; no new dependencies of any kind (house rule 1).
- **TDD**: the failing test is written and *seen to fail* before the code that satisfies it
  (house rule 2). For a guard, "seen to fail" means **mutation-tested** — break the thing it guards
  and watch it go red — because a guard that cannot fail is the defect this whole pass is about.
- **`SCHEMA_GENERATION` stays 49.** No new `db/NNN` file. Both SQL edits sit beside the definitions
  they govern, in the file that owns the object.
- **`CREATE OR REPLACE FUNCTION` preserves the existing ACL**, so a REVOKE belongs where a function
  is *first* defined; a later replacement needs none.
- **Guard before connect**: every DB-gated test takes `db::test_serial_guard(&base)` *before*
  `connect_and_load_schema`.
- **UUIDs bind as text** (`cairn-node` does not enable tokio-postgres's `with-uuid-1`): bind
  `&uuid.to_string()` and cast `$1::text::uuid`.
- **Files under 500 lines** (house rule 4).
- Nothing here changes any door's behaviour. Every item is a guard, a grant, or a test.

### Task 1 — #452: one source walk, not three

Three guard tests each roll their own recursive `.rs`/`.sql` walk. The argument for consolidating is
**not** line count: two of the three copies carry defects the third already fixed.

- `no_drugref_dependency.rs::trusted_sources` uses `p.is_dir()`, which **follows symlinks** — a
  symlink to an ancestor makes the walk unbounded (a hang in a required check, which reads as CI
  flakiness rather than as a defect).
- `event_log_row_by_name.rs::source_files` does `let Ok(entries) = read_dir(root) else { return }` —
  an unreadable directory contributes nothing and the guard passes, a silent failure inside a guard.
- `db_gate_actually_ran.rs` fixed both (`file_type()`, and a loud panic naming the path).

**Files:** create `crates/cairn-node/tests/common/sources.rs`; edit the three callers.

**Shape:** `#[path = "common/sources.rs"] mod sources;` — a **leaf** module, bypassing
`common/mod.rs`, whose first three lines are `use cairn_event::…` / `tokio_postgres::Client` /
`uuid::Uuid`. A pure source-inspection binary must not drag that in. It also keeps the new helper out
of `identity_scaffolding_shared.rs`'s derivation, which reads `common/mod.rs` specifically.

**Interface:** `pub fn source_files(roots: &[PathBuf], skip_dirs: &[&str], exts: &[&str]) -> Vec<PathBuf>`
— three parameters because the three copies genuinely differ (roots, skip sets, extensions).

**Verification:** the three suites stay green; mutation — point a root at a non-existent directory
and the walk must panic naming it, not return empty.

- [x] Write `common/sources.rs` with its own unit tests (symlink-safety, loud-on-unreadable).
- [x] Refactor the three callers; confirm each suite still passes.

### Task 2 — #449: the scan must read code, not prose

`gate_vars_read_by_the_suite` matches the literal prefix `CAIRN_TEST_` anywhere in any `.rs` file
under `crates/`. Prose therefore counts as a read: paraphrasing this repo's own worked example
(`CAIRN_TEST_PG4`) into a `//!` header reds the required `test` job, blaming the environment for a
variable nothing reads.

**Fix:** require the match to sit inside an `env::var("…")` / `env::var_os("…")` argument. Still
derived from two genuinely independent authorities (source text vs process environment), no longer
poisonable by a comment.

**Verification (mutation):** a doc-comment mention of `CAIRN_TEST_PG9` must NOT be picked up; a real
`env::var("CAIRN_TEST_PG9")` read MUST be. Both asserted as fixture tests over synthetic source
strings, so the parser is pinned regardless of what the real tree happens to contain.

- [x] Fixture tests over synthetic sources (prose ignored, call site found) — see them fail.
- [x] Implement the `env::var` argument parser; both fixtures pass; the three real names still found.

### Task 3 — #450: invert the polarity — fail closed

The guard binds only when `$CI` is set. `CI` is set in **zero** places in this repo — it is inherited
from the runner — so a scrubbed environment, a container without `-e CI`, or `env -i` silently
disables the one guard whose entire argument is that unverified assumptions are how a suite goes
green. It fails **open**; every other floor in this repo fails closed.

**Decision (maintainer, 2026-08-21): invert.** Assert by default; `CAIRN_ALLOW_DB_SKIP` opts out.

**The polarity subtlety, stated because it is the thing to get wrong:** `running_under_ci` treated an
unrecognised value as *CI* (fail-closed for that reading). An opt-out variable must treat an
unrecognised value as *not opting out* — the OPPOSITE default — or `CAIRN_ALLOW_DB_SKIP=please` reads
as permission and the guard fails open again. Only an explicit affirmative (`1`/`true`/`yes`/`on`,
trimmed, case-insensitive) opts out; everything else binds.

**Blast radius, checked before the change:** the only CI step that runs this binary is
`cargo test --locked --workspace` in `rust.yml`'s `test` job, which sets all three variables. The
`cargo test -p cairn-medication-view --features fixtures` step does not build cairn-node's test
binaries, and `cairn-gui` is a separate workspace.

- [x] Replace `running_under_ci` with the opt-out predicate; unit-test both polarities.
- [x] CONTRIBUTING: a "Running the tests locally" section naming the three variables and the opt-out.

### Task 4 — #451: the same hole, one language over

Fifteen `matcher/tests/` files self-skip on `CAIRN_TEST_PG`, and pytest reports a skip as a pass. A
typo in either workflow's `env:` block skips the whole suite and the run comes back **greener than
usual**.

**Shape:** a dedicated `matcher/tests/test_db_gate_actually_ran.py`, mirroring the Rust guard —
derive the variable names from the test sources (`os.environ.get("…")` / `os.getenv("…")` /
`os.environ["…"]`), assert each is usefully set, same `CAIRN_ALLOW_DB_SKIP` opt-out, same
empty-string-counts-as-missing rule.

**The step that must declare its intent:** `matcher.yml`'s `lint-test` job runs the pure suite
**deliberately** without a database. Under a bind-by-default guard that job must therefore carry
`CAIRN_ALLOW_DB_SKIP: "1"` in its `env:` — which is the fail-closed shape working as intended: the
run that means to skip the DB tier says so at the site that means it, and every other run is bound.

- [x] The guard test, with fixture tests over synthetic sources (as Task 2).
- [x] `matcher.yml`: declare the opt-out on the pytest step, with the reason inline.

### Task 5 — #453: the twin helpers join the REVOKE convention

#382 revoked the 22 `cairn_check_*` validators; #443 revoked `cairn_event_twin`, the dispatcher.
Four `cairn_twin_%` functions still hold Postgres's default EXECUTE-to-PUBLIC:
`cairn_twin_skeleton`, `cairn_twin_is_present` (db/005), `cairn_twin_is_authored`,
`cairn_twin_provenance_of` (db/015). The issue names two; the family is four, and revoking two of
four would recreate exactly the half-followed state #443 was about.

**Family shape:** a `cairn_twin_%` NAME PREFIX (escaped `\_`), so the next helper is covered with no
edit — the same reasoning `CHECK_FAMILY` gives, and for the same reason: there is no registry to read.

**THE LIVE CALLER, verified empirically, not assumed.** `event_twin_provenance` is a view
`GRANT SELECT`-ed to `cairn_agent`, and PostgreSQL checks functions called *inside a view* against
the **invoking** user, not the view owner. Measured on PG 18.1:

```
REVOKE EXECUTE ON FUNCTION cairn_twin_provenance_of(bytea) FROM PUBLIC;  SET ROLE cairn_agent;
SELECT count(*) FROM event_twin_provenance;
ERROR:  permission denied for function cairn_twin_provenance_of
```

and after granting that one, the **inner** call is checked too:

```
ERROR:  permission denied for function cairn_twin_is_present
CONTEXT:  PL/pgSQL function cairn_twin_provenance_of(bytea) line 6 at assignment
```

So the REVOKE must be paired with `GRANT EXECUTE … TO cairn_agent` on **both**
`cairn_twin_provenance_of` and `cairn_twin_is_present`, or the declared read surface breaks. Net
privilege change is still a narrowing: PUBLIC loses, one named role keeps.

Rejected: making `cairn_twin_provenance_of` `SECURITY DEFINER` to dodge the inner check. That points
owner privilege at a function taking arbitrary attacker-supplied `bytea` into a pgrx parser, and adds
another `search_path`-pinning obligation (#426) — a worse trade for a legibility fix.

- [x] Test first: `cairn_agent` can `SELECT` from `event_twin_provenance` (fails once the REVOKE
      lands without the GRANTs — that IS the mutation proof).
- [x] Fourth family in `floor_execute_grants.rs` (`cairn_twin_%`, floor 4).
- [x] The REVOKEs in db/005 + db/015 and the two GRANTs beside the view's own.

### Task 6 — #386: drive db/048, don't just load it

`schema_subset_alone_satisfies_every_door` states its job as driving every SQL entry point the subset
ships. db/049's half was closed; **db/048's was not**. Nothing ever calls `cairn_event_thread`,
`cairn_effective_sensitivity` or `cairn_thread_patient` on the medication-less subset schema — and
PL/pgSQL binds at first **execution**, so today the `to_regclass … RETURN NULL` guard bodies could be
deleted and the whole workspace would stay green; the first client read against a cairn-sync-shaped
node would then raise `relation "medication_statement" does not exist`.

**Second probe, currently unexercised anywhere at all.** `cairn_event_thread` probes a representative
table from *each* of db/031 and db/032 to cover a loader that crashed mid-replay between them. No
schema in the tree has 031 without 032, so the second probe has never decided anything. The subset
database can model that window exactly: create a bare `medication_statement` stub, leaving
`medication_dose_event` absent, and assert the call still answers NULL. Delete the second probe and
that assertion raises — a genuine, non-vacuous pin.

- [x] Drive `cairn_event_thread` / `cairn_effective_sensitivity` / `cairn_thread_patient` on the
      subset; assert NULL / `routine` / NULL.
- [x] Model the crash-mid-replay window with a stub table; assert NULL; drop the stub.

## What changed during implementation, and why it is recorded here

Two of the six tasks did not survive contact with the code as planned. Both corrections are the
substance of the pass, so they are appended rather than edited into the tasks above — the plan is the
record of what was intended, and the gap between intent and outcome is the part worth reading.

**Task 6 (#386): the planned fixture was vacuous, and only the mutation test said so.** The plan's
crash-mid-replay probe seeded a `medication_statement` stub and asserted `cairn_event_thread` still
answered NULL, reasoning that the seeded row proved the first probe was passing. It did — and the
assertion still proved nothing, because the *event* it was called on was a `patient.amended`. §10b's
type gate classifies `patient.%` as thread-free and returns NULL **before either probe is reached**.
Deleting the second `to_regclass` probe left the suite green. The fixture only became real once an
**ADR-0056 admit-uninterpreted event of a thread-BEARING type** (`observation.vital.recorded`,
applied through the remote door) was added — the realistic shape, since a peer one schema generation
ahead is exactly who sends one. Every event the subset test already authored carried a thread-free
prefix, which is why the gap was invisible.

**Task 5 (#453): the family was four, not two, and the REVOKE needed two GRANTs the issue did not
predict.** The issue named `cairn_twin_is_present` and `cairn_twin_skeleton`; `cairn_twin_is_authored`
and `cairn_twin_provenance_of` are the same family in db/015, and revoking two of four would have
recreated the half-followed state #443 was written about. The GRANTs are the more interesting half:
they were found by *measuring* the ACL behaviour on PG 18.1 rather than reasoning about it, which is
what the plan called for and what the issue's own "check the live callers first" warning asked for.

**Two tasks landed exactly as planned** (#449, #450), and one (#452) confirmed its own escape hatch
was not needed — the shared `(roots, skip_dirs, exts)` signature is simpler than three local walks,
so the issue's "closing as won't-fix is a legitimate outcome" branch was not taken.
