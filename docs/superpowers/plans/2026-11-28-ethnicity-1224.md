# Ethnicity in demographics (#1224) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A patient's ethnicity (Indigenous identity included) is recordable as a demographic answer, a
patient-stated answer is never displaced by any other source, and an advisory actor reads it from
`patient_demographic`.

**Architecture:** A new field `ethnicity` on the existing `demographic.field.asserted` spine. One
assertion is the patient's whole answer: `value` in plain words, optional `facets.codings`
`[{system, code, display}]`. A third winner ordering, `self-identified`, joins `provenance-first` and
`recency-first` in `cairn_demographic_field_policy`. The #1211 door and `patient-demographics` CLI gain
the fact.

**Tech Stack:** Rust (cairn-event, cairn-node), PL/pgSQL (db/013, db/014), tokio-postgres tests.

**Spec:** `docs/superpowers/specs/2026-11-28-ethnicity-1224-design.md`

## Global Constraints

- The field name is exactly `ethnicity`; the policy name is exactly `self-identified`.
- "Patient-stated" means `provenance = 'patient-stated'` exactly (the §4.1 ladder term).
- The order key for `self-identified` is
  `(provenance = 'patient-stated', hlc_wall, hlc_count, provenance_rank, origin COLLATE "C", value COLLATE "C", content_address)`.
- No jurisdiction's vocabulary in the core: `system`, `code` and `display` are open text; the floor never
  checks a value set.
- The SQL changes are **in-place edits** of `db/013` and `db/014` (ADR-0080; CONTRIBUTING allows it for a
  door the window never calls). No new `db/*.sql`, no `SCHEMA_GENERATION` bump: no node holds an
  ethnicity event (nothing in the tree writes one), so no re-projection heal is owed.
- `CREATE OR REPLACE` only — never DROP + CREATE (preserves the db/011 REVOKE; `floor_execute_grants.rs`).
- Any SQL edit needs a rebuild before a test sees it (db files are `include_str!`).
- No new event type, so `twin_registry.rs` / `db/tests/034` / projection-registry counts do not move.

## Review Focus

1. **A later non-patient answer after a patient-stated one** (an import saying "Not stated") — the
   patient's answer stays the winner. Pinned in Task 2.
2. **A later patient-stated decline after a patient-stated "Aboriginal"** — the decline wins (the
   patient's latest word). Pinned in Task 2.
3. **Malformed codings from a raw-SQL writer** (`codings` a string; an element without `display`; an
   element that is not an object) — refused with a legible message naming `ethnicity`; `codings`
   absent or `null` accepted. Pinned in Task 2.
4. **A coding whose display contains `|`**, and **`--ethnicity-coding` given without `--ethnicity`** —
   the display keeps the remainder after the second `|`; the lone coding is refused, not dropped.
   Pinned in Task 3.
5. **Equal-HLC ties and apply order** — two nodes applying the same pair in either order and under a
   locale collation converge on one winner. Pinned in Task 2 (the collation loop gains `ethnicity`).

## Paper-parity benchmark (§1.2)

- **Paper counterpart:** the ethnicity / "Are you of Aboriginal or Torres Strait Islander origin?" line
  on a paper registration form, ticked or written by the registrar from the patient's answer.
- **Steps:** paper N = 1 (tick or write the answer) → architecture M = 1 act (one assertion carrying the
  whole answer, several ethnicities included) → UI K = 1 field + the existing save, owed by the window
  slice. Correcting it: N = 1 (strike and rewrite) → M = 1 (record the new answer). Provenance is the
  one extra word the #1211 door already asks once per act, not per fact.
- **Time + cognitive load:** ≤ 5 s to record a stated ethnicity once the question is asked, the current
  answer readable without a click. Not measurable here (CLI only); owed by the slice that puts the field
  in the window.
