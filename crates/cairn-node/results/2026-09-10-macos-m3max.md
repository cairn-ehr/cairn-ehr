# DR restore paper-parity measurement — 2026-09-10, macOS M3 Max

> Produced by `scripts/measure_dr_restore.py`, following [`RUNBOOK.md`](RUNBOOK.md). This is one
> operator on one machine: an honest data point, not a study. It discharges the time half of the
> §1.2 budget [#512](https://github.com/cairn-ehr/cairn-ehr/issues/512) has owed since DR slice 1.

**Headline: a 100 003-event medium restores in 116.7 s against a budget of 600 s, and 85 000 sealed
bodies open on the restored node.** The budget is met with roughly 5× headroom.

## Corpus shape

Seeded by `cargo run --release --example seed_measurement_corpus`, in-process through the production
orchestrators — the same `submit_event` floor, born-sealed bodies (ADR-0052) and per-write human
authorship (ADR-0053) the CLI uses.

At the 5 000-patient point:

| Event type | Count | Sealed? |
|---|---:|:--|
| `clinical.medication.asserted` | 85 000 | **yes** |
| `demographic.field.asserted` | 10 002 | no |
| `identity.registration.asserted` | 5 001 | no |

**85 % of the medium is born-sealed clinical content**, which is the point: a corpus of demographics
alone carries no `event_dek` rows, so the restore's per-record unwrap and re-wrap — the expensive half
and the whole subject of ADR-0067 — would never run, and the figure would flatter the architecture.
Every medication assert is authored by an enrolled human actor, so the restore genuinely re-resolves
authors through `actor_current`.

Medium size at 100 003 events: **140 MB** (~1.4 KB/event).

## Measured — the curve

Only **Restore** is measured against the budget. Seed is context. Backup is reported for
[#552](https://github.com/cairn-ehr/cairn-ehr/issues/552).

| Events on medium | Seed (s) | Backup (s) | **Restore (s)** | Applied | ≤ 10 min |
|---:|---:|---:|---:|---:|:--|
| 2 003 | 1.9 | 0.5 | **2.6** | 2 003 | PASS |
| 20 003 | 18.9 | 2.9 | **20.0** | 20 003 | PASS |
| 50 003 | 49.5 | 7.7 | **58.2** | 50 003 | PASS |
| 100 003 | 134.7 | 15.0 | **116.7** | 100 003 | PASS |

**Shape: linear, and clean.** Fitting the two largest points gives **1.17 ms per event** with an
intercept indistinguishable from zero. Per-event cost across the whole curve:

| Events | ms/event |
|---:|---:|
| 2 003 | 1.30 |
| 20 003 | 1.00 |
| 50 003 | 1.16 |
| 100 003 | 1.17 |

No bend. That matters more than the headline number, because a linear restore means the budget has a
predictable ceiling rather than a cliff: **600 s is reached at roughly 510 000 events** on this
hardware. A solo clinic authoring 100 events a day would take about fourteen years to get there.

> A curve that bends is a finding even when every point passes. This one does not bend, so there is
> no finding here — stated explicitly rather than left as an empty section.

## Step count against the paper counterpart (§1.2)

Paper counterpart: the off-site duplicate chart. *N* = **2** (fetch the box; shelve it).

| # | Architecture-forced act | Bundled in a UI? |
|---|---|---|
| 1 | Attach the medium | no — physical, and it has a paper counterpart |
| 2 | Run `cairn-node restore --from <medium>`, entering the **new** key's operational passphrase | — |
| 3 | Enter the **old** node's recovery code at a second prompt | plausibly, see below |

*M* = **3** against *N* = **2**. `M > N` **stands, filed, not argued away** — but the excess act has
**changed identity**, and that is this run's most useful result after the timing.

DR slice 1's plan named the third act as *"confirm the echoed identity when provenance is not
sole-enroll-signed"*.
[ADR-0068](../../../docs/spec/decisions/0068-provenance-warns-never-gates-on-the-restore-path.md)
deleted that act: provenance warns and never gates, so there is no confirmation to give. The same plan
asserted that the escrow secret and the restore invocation were *"one interactive ceremony"*. **They
are not.** The recovery code is a second, separately-prompted secret, asked for after the node plane
has already been applied.

This is a better-posed problem than the one the plan filed. An identity confirmation has no paper
counterpart and could never be bundled away; a second secret prompt plausibly can be, which is what
keeps *K* = **2** believable. See [#572](https://github.com/cairn-ehr/cairn-ehr/issues/572).

**One secret, as promised.** The budget's *"one secret"* clause holds as written: only the recovery
code is *retained* from the dead node. The new key's passphrase is invented at restore time.

**No knowledge of the dead node's config**, also as promised, and now pinned mechanically rather than
measured — [`restore_needs_nothing_about_the_dead_node.rs`](../tests/restore_needs_nothing_about_the_dead_node.rs)
asserts against the real `--help` that `restore` requires only the medium and the new database, and
that `--superseded-node` stays optional.

## Findings

1. **[#572](https://github.com/cairn-ehr/cairn-ehr/issues/572) — a restore cannot be scripted at all,
   and the failure is silent-shaped.** The recovery code is read through `rpassword`, which opens
   `/dev/tty` and fails on any non-tty; it has no flag and no environment variable, unlike the new
   key's passphrase. A piped code does not merely fail to work — the read errors, the export never
   opens, and the restore recovers **zero patients** while exiting non-zero. Reproduced here verbatim.
   The rig has to allocate a pty, which is scaffolding that exists only to work around it. Filed from
   this run.

2. **[#552](https://github.com/cairn-ehr/cairn-ehr/issues/552) confirmed, with a number it did not
   have.** A single capture is linear (~0.15 ms/event), so the issue's *"O(whole medium)"* is not about
   one run being quadratic — it is about every run re-paying for everything. Measured directly: a
   **second capture of the same 100 003-event medium with ZERO new events cost 9.95 s**, against 15.0 s
   for the capture that wrote all 100 003. **About two thirds of a nightly capture's cost is
   independent of how much is new.** The issue's ~23 000-event estimate for crossing a 2 s budget is
   consistent with this curve, which puts the crossing at roughly 14 000.

3. **No finding against the restore budget itself.** 116.7 s against 600 s, linear, on the reference
   point #512 names. Recorded plainly because an absent finding has to be asserted, not inferred from
   an empty list.

## What this run does not establish

- **A single machine, and a fast one.** An M3 Max with NVMe is not a Raspberry Pi or an Android
  handset, and fractal topology means both are legitimate restore targets. The linear shape should
  carry; the constant will not. ADR-0067 already names **peak memory** as unbudgeted, and this run does
  not measure it — the reader materialises and sorts the servable clinical set, which at 140 MB of
  medium is comfortable here and may not be there.
- **A clean medium.** Every point restored completely. Nothing here measures a torn tail, a burned
  identity `seq` ([#549](https://github.com/cairn-ehr/cairn-ehr/issues/549)), an unopenable DEK
  ([#536](https://github.com/cairn-ehr/cairn-ehr/issues/536)) or a partially-drainable pen.
- **The wall-clock a human experiences.** The rig answers the prompt the instant it appears. A real
  operator is reading a warning, finding a card, and typing a 37-character code.
